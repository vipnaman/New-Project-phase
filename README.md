# RAKTA

RAKTA is a full-stack blood donation and emergency blood connection platform built with Flask, SQLAlchemy, and a responsive HTML/CSS/JS frontend.

## Features

- donor discovery and blood search
- donor registration and profile management
- blood request creation and lifecycle tracking
- emergency request workflow
- admin dashboard and analytics
- authentication, notifications, and protected APIs
- SQLite fallback for local development and PostgreSQL-ready configuration
- admin-reviewed donor profiles and verified hospital directory
- expiring requests with urgency-based lifetimes and requester cancellation
- bilateral donor/requester contact requests with phone sharing only after acceptance
- in-app notifications, optional SMTP email alerts, email delivery status, and user notification preferences
- admin activity audit records and global appearance controls
- donor and hospital listing reports with an administrator review queue
- requester account removal with profile anonymization
- CSRF protection for state-changing session-authenticated requests

## Environment variables

Create a `.env` file based on `.env.example` before running the app.
The development rate limiter uses in-memory storage. Keep that setting for local use only.

## Database setup

Default local development uses SQLite. PostgreSQL is supported via the `DATABASE_URL` environment value.

```bash
flask db upgrade
```

## Running locally

```bash
python run.py
```

Open `http://localhost:5000`.

## Administrator setup

Create the initial administrator from the project root:

```bash
flask --app run.py create-admin
```

The command defaults to `admin@gmail.com` and asks for the password twice using hidden terminal input. The password is stored as a hash. After provisioning, sign in through `/login`; administrator accounts are redirected to the protected `/admin` panel.

Alternatively, for the first local bootstrap only, configure a long random `ADMIN_SETUP_TOKEN` in `.env`. The login page then shows **Set up the initial administrator**. That one-time form only accepts `admin@gmail.com`, requires the setup token, and disappears after an administrator is created. Never reuse or publish the setup token; remove it from the environment after setup.

## Deployment

### Render free demo

The root `render.yaml` selects Render's free web service, PostgreSQL, and Redis-compatible Key Value plans. It is intended for a temporary demo only, not for a public blood-donation service or real user data. Free plans and availability can change; confirm the current prices in Render before creating the Blueprint. The application secret is generated by Render.

To publish:

1. Push this project to a GitHub repository that you control, excluding `.env`, local databases, and virtual environments.
2. In Render, choose **New → Blueprint**, connect the repository, and verify that each service is set to the **Free** plan before creating it. If Render presents a paid plan or requests a payment method, stop and review the selections; do not approve charges you do not want.
3. Wait for the database, Key Value, and web service to deploy successfully.
4. Create the first admin securely from the Render Shell using `flask --app run.py create-admin`; use a unique password and do not share it.
5. Test sign-in, donor review, request/contact flows, database migrations, and `/healthz`.

**Free-tier limitations:** the web service sleeps after inactivity and has an ephemeral filesystem; never use its local SQLite file for persistent data. The free PostgreSQL database is limited to 1 GB, expires 30 days after creation, has no backups, and is eventually deleted unless upgraded. Free Key Value data can be lost when it restarts, so rate-limit state resets. SMTP ports used for email are blocked on free web services, and this Blueprint does not create an expiry cron job. Requests are expired opportunistically when relevant app endpoints are visited; no background schedule runs while idle. Keep this deployment as a disposable demo with fake/test data only. Back up or export anything you need before the database expires.

For a reliable production deploy, upgrade to paid plans and provide a unique random `SECRET_KEY` of at least 32 characters, persistent PostgreSQL, shared Redis-compatible `RATELIMIT_STORAGE_URI`, scheduled request expiry, SMTP delivery, backups, and monitoring. The app refuses to start in production with placeholder/short application secrets or in-memory rate-limit storage. If using the web-based first-admin setup, configure a separate random `ADMIN_SETUP_TOKEN` of at least 32 characters; otherwise leave it unset and use the CLI setup. The free Render Blueprint runs database migrations at startup and starts Gunicorn with one worker:

```bash
flask --app run.py db upgrade && gunicorn --workers 1 --bind 0.0.0.0:$PORT run:app
```

Serve behind HTTPS; production session and remember-me cookies are marked Secure, HttpOnly, and SameSite=Lax. State-changing browser requests require the CSRF token embedded in RAKTA pages. Provision the administrator on the deployment host with `flask --app run.py create-admin`, entering the password only into the hidden terminal prompt. Never place production credentials in source control.

For email alerts, set `MAIL_SERVER`, `MAIL_PORT`, `MAIL_USERNAME`, `MAIL_PASSWORD`, `MAIL_DEFAULT_SENDER`, and TLS/SSL settings in the hosting secret store. In-app notifications continue to work if SMTP is unconfigured or temporarily unavailable; each notification records whether email was sent, failed, disabled, or not configured. Users can disable email alerts in Settings. SMS delivery is not included; connect and test a provider such as Twilio or an equivalent local service before advertising SMS alerts.

Donors remain hidden until an administrator reviews their account. Public donor responses omit email and phone. A requester/donor contact request shares phone numbers only after the recipient accepts. Requests expire after 6 hours (emergency), 1 day (urgent), or 3 days (normal); reads enforce expiry opportunistically. The `flask --app run.py expire-requests` command can be run manually, or scheduled on a paid plan.

Authenticated users can report donor and hospital listings for review. Reports are not an emergency service; they require administrator follow-up. Account removal disables sign-in and anonymizes personal profile information. Configure and test a documented retention policy, restore procedure, monitoring, and legal notices with the deployment team before inviting real users.

## Security notes

- never commit `.env`
- hash user passwords
- validate all inputs on the server
- restrict admin routes to authorized users
- keep API responses privacy-aware
- review privacy, consent, retention, and emergency-service wording with qualified counsel for each operating region
